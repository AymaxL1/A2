# 05 — 决定:dangerous 确认模型重设计

Type: grilling
Status: resolved

Blocked by: 01, 02

## Question

替代 [ADR 0005](../../../docs/adr/0005-agent-first-interaction.md) 第 4 条(「最终确认必须落宿主 GUI」)的新模型:

1. **无 GUI 在场时 dangerous call 的行为**:结构化拒绝(fail-closed,提示装壳/等壳)?采 02 票某替代确认面(通知动作按钮 / Touch ID / 预授权 token+TTL)?还是按 01 票第 3/4 问的强度裁「无 GUI = dangerous 不可用」?
2. **GUI 在场时**它仍是首选确认面吗?内核如何发现「有壳在场」(注册/心跳)?
3. **防「agent 替用户确认」的底线**在新模型如何保持(02 票防御力评估为输入);`--yes` 类旁路仍然禁止?
4. **CLI 永不交互阻塞**(0005 第 3 条)保持不动?TTY 在场时(人手敲 `aa` 的场景)允许交互确认吗?
5. **agent-delegation 连带**:其 spec 押在旧模型上的审批环,给出修订方向(细节留给该效fort)。
6. **跨端确认代理**:01 票已裁内核跨端为当下承诺、无 GUI 一等公民且 dangerous 无确认代理时默拒——非 mac 端(无菜单栏壳可降格)确认代理的形态或预留,由本票一并裁。

## Answer

2026-08-04 现场面试五问钉死(用户逐项拍板),以下替代 ADR 0005 第 4 条:

1. **三层叠加模型**(主体结论):
   - ① 无确认器在场 → 结构化默拒 `confirmation_unavailable`,fail-closed(01 票 canon 的落实);
   - ② **拒绝报文即指引**:拒绝中携带机器可读的「人类如何完成」精确命令——AI agent 只**转告**,人类自己执行。这是无 GUI 端的零基建默认路径;
   - ③ 有注册确认器时升级为**带外确认**:mac = 菜单栏壳(Touch ID/点按),确认信息永不过 AI agent 之手;
   - `--yes` 类旁路继续禁止。dangerous 可用性随在场确认面分级,不一刀切。
   - 技术底盘(02 票事实):同 UID、无 GUI 时内核无法分辨「人敲的」与「agent 跑的」,故一切经 agent 之手的「确认」一律视同自批、不承认。
2. **在场发现 = 长连接即在场**:确认器经 UDS 注册 confirm-agent 角色并保持长连接;连接在=在场,断线=内核立即降回默拒层。无轮询、无心跳包、无陈旧状态窗口;内核校验对端 UID(`getpeereid`,11 票已在 Bun/`bun:ffi` 实测打通)。确认器在场时自动成为首选确认面。
3. **TTY 交互确认禁止**:保持 ADR 0005 第 3 条「CLI 永不交互阻塞」不动;`isatty` 不构成人类证明(agent 可开伪终端仿冒)。人在终端的场景由第②层覆盖。
4. **跨端确认器只定协议插槽**:本图钉死确认器协议(UDS 注册角色 / 长连接即在场 / 对端 UID 校验 / 确认请求-响应报文),V1 唯一实现 = mac 菜单栏壳;Linux 端 V1 无确认器,dangerous 默拒即设计行为;带外通道(手机推送 + token 回填等)将来按协议接入,不进本图。
5. **agent-delegation 修订方向 = 审批面收敛到内核统一仲裁**:delegation 执行器的 dangerous 与普通调用走同一套三层仲裁(同确认器通道/同默拒/同禁旁路),内核统一 audit 记账;无确认器时「拒绝即指引」结构化回传发起方。细节留给该效fort。

**术语钉死**(domain-modeling):「确认代理」在本项目与网络代理(mihomo)、AI agent 双双撞名,统一改称 **确认器**(英文 confirm agent)——替人类出面呈现确认并安全回传批准的进程;它是「防 AI agent 自批」机制的执行者。后续 ADR/文档一律用此词。
