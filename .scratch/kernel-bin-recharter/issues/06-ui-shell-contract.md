# 06 — 决定:UI 壳新契约

Type: grilling
Status: resolved

Blocked by: 04, 05

## Question

菜单栏壳降为内核的可选纯客户端后:

1. **壳↔内核走哪条面**:与 `aa` 同一 capability 面(纯对等客户端)?还是壳持有特权通道(dangerous 确认请求推送、事件订阅)?05 票结论需要壳侧什么接口?
2. **状态同步机制**:菜单栏显示的代理状态/节点列表怎么来(轮询 / UDS 推送);现 `MenuBarController` 直读 runtime 的地方全部改客户端调用?
3. **UI 资产去留**:`AAUISystem`、`menu-snapshot`(一个模型两个渲染器)与快照测试体系怎么跟着动;XcodeGen .app 壳工程的形态。
4. **V1 仍交付壳吗**?壳缺席/崩溃时内核的非确认类行为(通知?静默?);「退出即还原」等现挂在 GUI 生命周期上的语义归谁。

## Answer

2026-08-04 现场面试四问钉死(用户逐项拍板):

1. **通道 = 对等客户端 + 角色注册,V1 不验签**:壳与 `aa` 走同一条 UDS capability 面,无特权通道;确认器(confirm-agent)与订阅者(subscriber)只是长连接上注册的角色。同 UID 冒名注册确认器记为**已知边界**——02 票威胁模型:同 UID 敌意进程本就能绕开内核直接作恶,仲裁保护的是受认可路径,不对抗同 UID 恶意代码;注册协议预留身份强化字段(将来可加 cdhash/团队 ID 校验),Linux 无对等物也因此不受阻。05 票需要的壳侧接口 = 确认请求-响应报文 + 长连接在场语义,别无其他。
2. **状态同步 = 长连接订阅推送**:subscriber 角色连上先收全量快照、之后内核有变化推增量(代理状态/节点列表/mihomo 存活);壳侧模型改为**内核事件流的投影**,`MenuBarController` 直读 runtime 的地方全部改客户端调用;零轮询、无陈旧窗口,与 05 票「长连接即在场」同一套机制。
3. **UI 资产全套保留、改喂养源**:`AAUISystem`/`menu-snapshot`「一个模型两个渲染器」模式保留——模型数据源从 runtime 直读改为事件投影,渲染器与手搓快照测试**原封不动**,继续当壳侧回归门禁;XcodeGen .app 壳工程保留(Touch ID/系统通知要求 bundle 身份,02 票事实);内核逻辑退场后 Swift 包的壳 target 群自然瘦身(target 细目归 07 票)。
4. **V1 交付壳;无壳静默;「退出即还原」废除**:V1 交付菜单栏壳(确认器唯一实现 + 状态投影,05 票依赖);壳缺席/崩溃时内核**静默运行**——事件入日志、CLI 可查、dangerous 自动降回默拒层(05 票断线即降级的自然后果;裸 bin 发不了系统通知是 02 票钉死的平台事实,静默是仅有的诚实选项)。**「退出即还原」语义废除**:系统代理等还原动作改挂内核显式命令(命名归 07 票),壳退出仅是客户端断连、代理照跑——数据面不随窗口起落。agent-delegation 在壳侧无专属通道,其 spec 修订指令随 08 票下达。
