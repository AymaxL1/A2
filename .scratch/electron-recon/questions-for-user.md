## 0. 一页速览

**两条路线「今天」的对照(01 票结论表+E1 实测):**

| | 切 Electron | 留 Swift |
|---|---|---|
| 今天能否动工 | **能**(E1 已实证:用户态装 Node 51s + Electron 20s,悬浮窗+UDS 冒烟全通,全程零 Xcode/CLT/sudo) | **不能**(SPM 清单解析/xcodebuild/XCUITest 均缺;vfsoverlay 绕过法只够单文件直编,够不到正式架构) |
| 解卡动作 | 无(已通) | 装完整 Xcode.app + 一次 sudo(下载+安装约 1 小时级,一次性) |
| 正式分发前提 | Developer ID 证书(**两栈相同**,notarytool 均不需 Xcode.app) | 同左 |
| 结构性代价 | 常驻内存 3–5 倍(E1 实测 4 进程 ≈287MB vs Swift 菜单栏 30–80MB,消不掉);8 周 major、仅支持最近 3 个版本(无 LTS);置顶窗与全屏 App 抢层级属多年 wontfix 类问题;S1/S2 已验资产需重写 | 语料密度差距;年度 SDK 升级纪律;AI 自读兜底缺失(但见下条) |

**今晚推翻/修正的旧认知(裁决权重变化):**

1. **「XCUITest 弱一档」不再构成切栈理由**——非 DOM 面(Tray/原生菜单/系统弹窗)的 E2E 两栈同弱,只能白盒打桩(05 票)。
2. **AI 闭环速度差距被高估**——S1 实证 Swift 热缓存编译约 1s,与 TS 热载同量级;真正卡住 Swift 的是本机工具链损坏(环境问题),不是语言(05 票)。
3. **「无签名通知崩溃」不能类比**——那是 Swift 侧行为;Electron 未签名只是通知静默失败,app 不崩(01/04 票)。
4. **签名/公证不是 Electron 的相对优势**——两栈都卡在同一张 Developer ID 证书上,工具链侧两边都齐(01 票)。
5. **自读兜底只恢复一半**——你能读回 manifest/契约层 TS,但域逻辑正确性还是靠 AI+测试(05 票)。

**Electron 侧今晚坐实的硬优势:** 开发循环彻底免 Xcode(实测);Linux CI 可跑域层测试(mac runner 约 10 倍价,06 票);将来 Windows 从「含核心全重写」降为「适配包+独立签名流程」(06 票);UDS/CLI/S3 沙箱结论全部平移无损(03 票)。

**Electron 侧今晚坐实的硬代价:** 内存 3–5 倍结构性;置顶 vs 全屏 App 抢层级 wontfix(02 票,详见 A5);透明窗丢系统阴影、全空间缺 `stationary` 位、跨屏拖拽跳变(02 票);安全窗口约 5.5 个月/版,升级跑步机停不下来(04 票)。

**待重验小口径:** E1 实装的是 Electron 33.4.11(npm 镜像滞后;registry latest=43.2.0)。结论方向不受影响,但终裁前建议在 43.x 上重跑一遍 E1(几分钟的事)。

## A. 必须答——不答无法终裁

### A1. 「通用」到底指什么?(08 票)

- **(a) 开发环境通用**:任何机器(无 Xcode 的 Mac、Linux CI)都能开发/测试。→ 事实:**成立**,唯 mac 打包/签名仍须真机 mac(Apple 限制)。
- **(b) 产品跨平台**:将来出 Windows 版。→ 事实:**部分成立**,栈无关层+UDS→named pipe 几乎免费,但 Tray/点透/通知要真机适配,Authenticode 签名要硬件 token/云 HSM(和 mac 证书完全两套)。

请选:只有 (a) / 只有 (b) / 都要 / 其他:____
(若只有 (a):Mac-only 的 ADR 0001 不用动。)

### A2. 「快速开发出初版」和一次性环境成本的取舍

你的原话:「我的诉求是希望把初版快速开发出来,不希望 Xcode 卡我进度。」对照已实测:

- **留 Swift**:装一次 Xcode(约 1 小时级,期间不用盯)→ 工具链根治,S1/S2/S3 已验资产全保,Phase 0 直接开工。
- **切 Electron**:今天就能动工(已实证)→ 但 S1/S2 要在 Electron 重做,ADR/路线要修订,并长期背 3–5 倍内存与 8 周升级节奏。

问题:你要消除的是**这一次环境阻塞**,还是**长期不想跟苹果工具链打交道**(年度 SDK 升级、XCUITest、打包每一步都在它手里)?——前者指向留 Swift,后者才是 Electron 的真正理由。

### A3. 终裁与旧决定的关系(09 票)

路线图写过:Phase 0 收尾对 Electron 回退「裁决一次,之后不回头」,且三条硬门**全没触发**——Swift 是三战三捷后被工具链问题追击的。若明天翻案 ADR 0002,需要你亲口确认:**这是新动机(进度/工具链)构成新判据,不是推翻当时的技术判断**。裁决文会照此措辞,免得将来反复。

### A4. 签名身份现状(两栈都躲不开)

钥匙串 0 个签名证书。有 Apple Developer 账号吗(个人/公司)?预计何时需要对外分发?(这决定 Phase 3 何时必须办证书;开发期两栈都可无证书干活,只是通知功能受限。)

### A5. 宠物窗压在全屏 App 之上,是不是硬需求?(02 票最大风险)

S1(Swift)已验证全屏辅助没问题;Electron 侧「置顶窗与全屏 App 抢层级」是 2017/2022/2023 三度报告、均被 wontfix 类关闭的问题。若「宠物在全屏视频/游戏上也要在」是硬需求,切 Electron 前**必须**把这条加进 E1 真机验证(今晚的自检读回值覆盖不了它);若可接受「全屏时宠物退场」,该风险降级。请表态。
